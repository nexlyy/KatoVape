# Миграции: что накатано и как накатывать дальше

Проект слинкован с CLI, миграции катятся из корня:

```bash
supabase db push
```

Порядок по номерам, все миграции идемпотентны: повторный запуск ничего не сломает.
Посмотреть, что уже в облаке:

```bash
supabase migration list --linked
```

## Состояние на 03.08.2026

Применены с 0001 по 0046. Не накачены 0047, 0048 и 0049, они лежат в репозитории и ждут
`db push`.

Вся схема одним файлом лежит в `supabase/apply_all.sql` на случай, когда CLI недоступен и
поднимать надо через SQL-редактор. Файл собирается командой и сам себя не обновляет:

```bash
npm run schema
```

0036 закрывает `promo_check` от анонима: коды короткие и человеческие, их подбирали словарём.
Проверить код теперь может только вошедший, а оформить заказ гость и так не мог.

0037 возвращает лимиты броней, которые 0014 случайно отключила для гостей: считаем по
`user_id` и `telegram_id` сразу, бронь без владельца отклоняем, больше трёх броней на человека
не даём.

0038 оживляет CRM: заказ и бронь сами заводят карточку клиента по телефону, телеграму или
аккаунту, заметку видит только автор с владельцем, а заблокированный контакт не может ни
заказать, ни забронировать.

0039 добавляет склад и деньги: поставки партиями с закупочной ценой, списание FIFO при выдаче
заказа, документы списания, расходы по категориям и отчёт по прибыли. Расходы и отчёт видит
только владелец.

0040 заводит долю менеджера: процент хранится историей со своей датой начала, к заказу
применяется та ставка, что действовала в день заказа. По умолчанию считается с прибыли по
заказу, то есть с выручки за вычетом закупки товара, но до расходов города.

0041 добавляет роль «управляющий», закрывает склад и закупочные цены от менеджера города и
чинит главное: выдача заказа наконец уменьшает остаток на витрине, а не только списывает
партии.

0042 правит 0041: переменная в триггере называлась `qty` и затеняла колонку `products.qty`,
списание падало на «column reference qty is ambiguous».

0043 разносит проценты по категориям товара, заводит справочник категорий, метки товара
вместо одной галочки «хит», напоминания менеджеру и подтягивает в карточки клиентов тех, кто
пришёл из бота и с сайта, а не только из заказа.

0044 меняет пустую категорию у ставки с NULL на пустую строку: из-за NULL уникальный ключ был
по выражению, и панель не могла сохранить ставку через upsert.

0045 добавляет `products.cost`: партии дают точную себестоимость только тому, что пришло
поставкой, а товар, лежавший на полке до появления учёта, списывался с нулевой стоимостью, и
маржа по нему равнялась выручке.

0046 считает открытые напоминания в сводке.

0047 заводит журнал движения товара: каждое изменение `products.qty` пишет строку с разницей,
причиной и остатком после. Поставка, продажа, списание и бронь называют себя сами, всё
остальное считается ручной правкой. Отсюда же берётся раздел «Движение товара» на дашборде
(функция `dash_stock`).

0048 возвращает в отчёт по выплатам действующую ставку: после 0043 она пропала из ответа, и в
«Финансах» колонка «Ставка сейчас» у всех показывала прочерк.

0049 не даёт опечатке во вкусе завести фантомный товар. Проведение искало строку по точному
совпадению и, не найдя, заводило новую позицию: задумано это было для товара, которого в
городе ещё нет, но срабатывало и на «Sour Aple» вместо «Sour Apple». Теперь документ сперва
проверяется целиком: нет товара с таким id вовсе, значит позиция новая и это нормально; товар
есть, а вкуса нет, значит опечатка, и проведение останавливается с названием строки.

Что стоит знать про последние:

0030 и 0031 (дашборд) всегда идут парой. 0030 заводит функции `dash_*` и выдаёт право звать
их роли `authenticated`, а доступ держит `is_owner_or_dev()`. В 0030 этот предикат возвращал
`null` для обычного покупателя, а `if not null` в PL/pgSQL не срабатывает, то есть отчёт по
выручке и клиентам был бы доступен любому вошедшему. 0031 оборачивает предикат в
`coalesce(..., false)`. Если придётся раскатывать схему с нуля, 0031 обязана идти сразу
за 0030.

0032 и 0033 (CRM) завели таблицы `contacts`, `contact_notes`, `crm_tags`, `cancel_reasons`,
`audit_log` и поля `orders.contact_id`, `source`, `manager_id`. Кодом они пока не
используются. Заодно 0032 расширила список статусов заказа значениями `packed` и `shipped`:
их никто не проставляет, но витрина, бот и панель их понимают и подписывают.

0034 закрывает функции, которые зовёт только сервер. Любая функция схемы доступна с
публичным ключом, поэтому `restock_list`, `audit`, `login_availability` и `bump_demand`
отозваны у `public`, `anon` и `authenticated` и выданы `service_role`. Там же заводится
таблица `auth_attempts`, по которой функция входа считает неудачные попытки.

0035 не доверяет полям брони, которые браузер пишет напрямую: триггер подставляет название
товара из каталога, а время брони обязано выглядеть как `ЧЧ:ММ`.

Проверить дашборд после раскатки: владелец видит вкладку с цифрами, обычный аккаунт получает
на `dash_kpi` ошибку прав (`42501`).

## Особый случай: 0047 и чистка базы

0047 вешает триггер на `products`, поэтому любая правка остатка после неё пишет строку в
`stock_moves`. Скрипт `supabase/maintenance/reset-test-data.sql` на это рассчитывает: он
чистит журнал последним, уже после обнуления остатков, иначе собрал бы обратно мусор от
собственной работы. Порядок один: сначала `supabase db push`, потом чистка.

Проверить после раскатки: провести поставку и убедиться, что в разделе «Движение товара»
появилась строка с причиной «поставка», а остаток на графике поднялся ровно на её количество.
Потом поправить остаток руками в карточке товара: строка должна назваться «правка руками».

## Если история разойдётся со схемой

Так уже было: схему до 0022 накатывали руками через SQL-редактор, CLI об этом не знал, и
`db push` попытался бы прогнать всё с 0001. История приводится в соответствие с реальностью
без правки схемы:

```bash
supabase migration repair --status applied 0001 0002 ... 0022
```

Команда пишет только в служебную таблицу `supabase_migrations.schema_migrations`. Лечится
это всегда одинаково: сначала `supabase migration list --linked`, потом `repair` на то, что
уже стоит в базе.

## Особый случай: 0026

Миграция забирает у браузера право писать в таблицу `orders`. С этого момента заказы заводит
только функция `create-order`, которая считает сумму сама. Если применить её раньше, чем
задеплоена функция и выложена витрина, оформление заказа перестанет работать у всех.

Порядок был такой: сначала `supabase functions deploy create-order`, потом `git push` и
ожидание сборки Pages, и только затем `supabase db push`. Тот же порядок понадобится, если
схему когда-нибудь будут поднимать заново.

Проверка после: заказ с оплатой при выдаче проходит на сайте и в мини-аппе, в панели он виден
с правильной суммой, а прямая вставка в `orders` с чужой ценой возвращает ошибку прав.

```bash
curl -X POST "$SUPABASE_URL/rest/v1/orders" \
  -H "apikey: $ANON_KEY" -H "Authorization: Bearer $USER_JWT" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"<свой id>","city":"katowice","items":[],"sum":1,"delivery":"pickup"}'
```
