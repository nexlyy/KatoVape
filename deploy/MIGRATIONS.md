# Миграции: что накатано и как накатывать дальше

Все миграции идемпотентны: повторный запуск ничего не сломает.

## Состояние на 31.07.2026

Применены **0001–0029**: функции задеплоены, подмена цены закрыта.

**Ждут применения 0030 и 0031 — дашборд.** Накатывать их только вместе и подряд.
0030 заводит функции `dash_*` и выдаёт право их звать роли `authenticated`, а проверку
доступа держит `is_owner_or_dev()`. В 0030 эта проверка возвращает `null` для обычного
покупателя, а `if not null` в PL/pgSQL не срабатывает — то есть между 0030 и 0031 любой
вошедший в магазин человек может прочитать выручку, средний чек и список клиентов.
0031 переписывает предикат через `coalesce(..., false)` и закрывает это.

```bash
supabase db push          # возьмёт 0030 и 0031 по порядку
```

Проверить после: владелец видит вкладку «Дашборд» с цифрами, а обычный аккаунт получает
на `dash_kpi` ошибку прав (`42501`).

`0032_crm_contacts.sql` и `0033_crm_operations.sql` — черновики CRM, кодом пока никто не
пользуется. Не накатывать: 0032 расширяет список статусов заказа (`packed`, `shipped`),
а панель, бот и витрина таких статусов ещё не знают и покажут сырой код.

История миграций в облаке была пустой: схему до 0022 накатывали руками через SQL-редактор,
и CLI об этом не знал — `db push` попытался бы прогнать всё с 0001. Историю привели
в соответствие с реальностью, схему при этом не трогали:

```bash
supabase migration repair --status applied 0001 0002 ... 0022
```

Команда пишет только в служебную таблицу `supabase_migrations.schema_migrations`.
Если в будущем снова появится расхождение (кто-то правил схему руками), лечится так же:
сначала `supabase migration list --linked`, потом `repair` на то, что уже в базе.

## 0023, 0024, 0025 — обычные

Накатываются как всегда:

```bash
supabase db push
```

Что проверить после:

- **0023** — в панели, раздел «Рассылка», появилось поле «Кому». У менеджера города там
  только его город, у владельца есть вариант «всем городам». Заведите тестовую рассылку
  на свой город: она должна сохраниться без ошибки.
- **0024** — оплата картой с промокодом списывает сумму со скидкой, а не полную.
  Если карта выключена (`PAYMENTS_CARD_OFF: true`), проверять нечего, миграция просто
  выдаёт право функции.
- **0025** — в разделе «Ассортимент» поставьте галочку «Хит», нажмите «Применить»,
  обновите страницу. Галочка должна остаться, а товар — встать первым в каталоге.

Если после 0025 панель всё ещё пишет про неизвестное поле, обновите кеш схемы вручную:
Supabase → Settings → API → **Reload schema**. Миграция просит об этом сама
(`notify pgrst, 'reload schema'`), но на некоторых планах уведомление доходит не сразу.

## 0026 — цена заказа, порядок обязателен

Миграция забирает у браузера право писать в таблицу `orders`. С этого момента заказы
заводит только функция `create-order`, которая считает сумму сама. **Если применить
миграцию раньше, чем задеплоена функция, оформление заказа перестанет работать.**

### Шаг 1. Задеплоить функцию

```bash
supabase functions deploy create-order
```

Функции нужны те же секреты, что и оплате. Проверьте, что они заданы:

```bash
supabase secrets list
```

Нужны `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CATALOG_BASE`
и `TELEGRAM_BOT_TOKEN` (последний — чтобы принимать заказы из мини-аппа по подписи).
`CATALOG_BASE` — адрес, откуда функция читает `data/products.json`, тот же, что у оплаты.

### Шаг 1.5. Выложить витрину — обязательно до миграции

Функцию зовёт новый `shared/auth.js`. Пока на GitHub Pages лежит старый, витрина умеет
только прямую запись в `orders` — ровно то, что миграция запрещает. Применить 0026 раньше
выкладки сайта означает сломать оформление у всех, даже при живой функции.

```bash
git push
```

Дождитесь, пока отработает Actions (workflow `Deploy Jekyll with GitHub Pages`), откройте
витрину и обновите страницу с очисткой кеша. Версии скриптов в ссылках должны смениться —
за это отвечает `npm run stamp`.

### Шаг 2. Проверить, что заказы проходят

До миграции витрина работает в обоих режимах: если функции нет, она молча возвращается
к прямой записи. Поэтому проверять надо предметно.

1. Оформите тестовый заказ с оплатой при выдаче — на сайте и в мини-аппе.
2. Откройте панель: заказ должен появиться с правильной суммой.
3. Убедитесь, что сумму посчитала функция, а не браузер: в логах должно быть обращение.

```bash
supabase db query --linked "select id, sum, amount, telegram_id from public.orders order by id desc limit 3;"
```

Отдельно стоит проверить корзину с оптовой ступенью и корзину с промокодом — именно там
сумма считается сложнее всего.

### Шаг 3. Применить миграцию

Остальные миграции уже применены, так что `db push` возьмёт только 0026:

```bash
supabase db push
```

### Шаг 4. Проверить ещё раз

Оформите заказ снова, теми же двумя путями. Если что-то пойдёт не так, в консоли браузера
будет ошибка от `create-order`, а не молчаливый отказ.

Заодно убедитесь, что подмена цены больше не проходит. Запрос ниже до миграции создавал
заказ на 1 zł, после — должен вернуть ошибку прав:

```bash
curl -X POST "$SUPABASE_URL/rest/v1/orders" \
  -H "apikey: $ANON_KEY" -H "Authorization: Bearer $USER_JWT" \
  -H "Content-Type: application/json" \
  -d '{"user_id":"<свой id>","city":"katowice","items":[],"sum":1,"delivery":"pickup"}'
```

### Если что-то сломалось

Откат — вернуть права на вставку:

```sql
create policy ord_own_ins on public.orders for insert with check (auth.uid() = user_id);
grant insert on table public.orders to authenticated;
```

После этого витрина снова начнёт писать заказы напрямую (и дыра с подменой цены
вернётся), поэтому откат — только на время разбирательства.

## Проверка перед выкладкой

Локальные тесты не ходят в базу, но ловят расхождение расчёта на витрине и на сервере:

```bash
npm test
```
